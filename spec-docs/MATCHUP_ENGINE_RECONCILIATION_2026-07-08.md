## 2. THE RECONCILED DESIGN (the engine's v1 shape)

### 2.1 Scope and entities

- **Pair scope: pitcher↔batter only, v1.** This matches the vision text, the data reality (the H2H substrate is `at_bat_events` keyed by batter/pitcher — `getMatchupEvents(batterId, pitcherId, {excludeGameId})`, `src/utils/eventLog.ts:1695-1720`), and keeps the surface small. Any-pair generalization is post-v1.
- **Season scope:** edges are season-scoped by construction (`RelationshipEdgeRow` keys `franchiseId/seasonId/statsScopeId`, `franchiseRelationshipEdgesStorage.ts:9-13,23-28`; franchise invariant statsScopeId===seasonId). v1 is one season (LSD §1), so the career-vs-season fork is moot; the display aggregate stays all-games as shipped.
- **The H2H aggregate is a read-side derivation, not stored state.** `getMatchupEvents` + `buildFenwayMatchupSummary` (`src/src_figma/app/utils/fenwayBoardContext.ts:52`) already produce the full lifetime line. The engine adds one **pure function** (new, `src/engines/matchupHeat.ts`): given the pair's ordered PA events and a game number, return `{ lifetime: {pa,h,hr,avg}, recent: {window:N, h, hr, line}, heat: [0,1] }` — deterministic, replay-idempotent, no store. Recent window default **N=10 PA** (§16 SIM-TUNE placeholder, captain-defaulted per C13).
- **The edge entity:** a matchup-born rivalry is a standard `RelationshipEdgeRow` with `type:'RIVALRY'`, **`formationSource:'matchup'`** (union extension at `franchiseRelationshipEdgesStorage.ts:40`), `potential:false`, `formedAtGameNumber` = the game that crossed the threshold. No new fields required for v1 (heat is recomputed, not cached); if profiling later demands a cached summary, it is an optional additive field on the row — still no DB bump.

### 2.2 Formation + intensity (how a matchup becomes, and feeds, a rivalry)

- **New per-game writer** `franchiseRelationshipMatchupCompute.ts` (mirrors the overtake writer's shape), tapped in `processCompletedGame` beside the existing four L13 taps (formation `:1427`, overtake `:1432`, intensity `:1437`, morale `:1442`). Per completed game: for each unique batter↔pitcher pair that met **in this game**, compute matchup heat (lifetime + recent via `getMatchupEvents` with `excludeGameId` + the game's own events); ~~if heat ≥ the formation threshold~~ **[RULED-UPDATE 2026-07-08, OQ-1: the spawn criterion is MUTUAL-WPA — spawn only when BOTH players' per-pair tallies of positive-WPA plate appearances against each other exceed the threshold; one-sided domination never spawns (domination = reporter narration only); thresholds = §16 placeholders]** → **create-if-absent** a `RIVALRY` edge with `formationSource:'matchup'`. Bounded by the game's unique PA pairs (~20-40).
- **Create-if-absent / no-clobber (the envy-ruling consumption):** the edge id is pair+type-canonical (`franchiseRelationshipEdgeId`, `franchiseRelationshipEdgesStorage.ts:94-109`), so a pair that already carries an envy/asg-snub/personality RIVALRY collides on the same row. Follow the shipped overtake precedent exactly: preserve `createdAt`/`formedAtGameNumber`/`formationSource` of the existing row, take `Math.max` on intensity (`franchiseRelationshipOvertakeCompute.ts:86-88`); "a later [event] on the same pair may relabel the edge (benign, invariant-clean)" per RIVALRY-ENVY-2B. Matchup formation intensity is computed **from the real game state** (the 2B pattern), NOT given the `'envy'` intensity carve-out.
- **Intensity/decay: reuse the shipped lifecycle wholesale.** Per-game deterministic recompute from stable fields (`computeRelationshipIntensity`, `src/engines/relationshipIntensity.ts:125-176`): baseline − cumulative ramped decay (base 0.012/game, compound 0.08, cap 0.06/game) + charged-matchup bump 0.14; dissolve below 0.25 (`:33-43`). **One addition:** a deterministic `matchupHeat` term in the recompute for `formationSource:'matchup'` edges (and as an intensity booster for existing RIVALRY edges between pairs who met this game), so a hot H2H sustains the edge against decay and a cooling one lets it dissolve naturally. Because heat is recomputed from the event log at any game number, replay-idempotency is preserved — the same property the engine header guarantees (`relationshipIntensity.ts:4-6`).
- **Exclusions:** ~~`formationSource:'overtake'` edges (HISTORY-inert per C2) are never formation/intensity inputs.~~ **[RULED-UPDATE 2026-07-08: overtake edges are RIVALRY and ARE formation/intensity inputs like any other rivalry edge — no overtake exclusion anywhere in this engine; the only guard is no second morale hit at the overtake moment itself.]** `rivalryScores` untouched (C11). REL-8: once the captain→chemistry governor lands (builds in the morale wave, V1_CANON:206 ruling 3), matchup-edge formation goes through the same threshold-shift suppression as every other edge — cross-team note: REL-8's captain governs his own clubhouse, so suppression applies to the rival-edge's effect on his player, not to the opposing player.

### 2.3 The REL-6 boundary (no duplicate mechanic — precise)

| Mechanic | Owner | Trigger | Cadence | Effect |
|---|---|---|---|---|
| **Charged matchup (game)** | REL-6, LOCKED — shipped as `isChargedRelationshipMatchup` + `buildRelationshipChargedMatchupEvent` (`franchiseRelationshipMoraleCompute.ts:224-233,386`; detection `franchiseRelationshipIntensityCompute.ts:102-109`) | Live edge, players on opposing teams (to be tightened to spec: + former-team leg, + HISTORY-edge leg, + type-awareness — SOT_REGISTER:242,336) | Per game, at pCG | Amplifies **that game's** morale swing, personality-scaled; +0.14 intensity bump; reporter pre-narrates |

Rules that keep them disjoint: (1) the game-outcome amplification belongs **only** to REL-6 — the engine's per-PA deltas exclude the game result; (2) the per-PA channel fires **only for rival pairs**, so a REL-6-charged game between, say, former friends gets no per-PA channel; (3) both land in the same pCG morale tap so the no-double-count audit is one code path; (4) stakes-scaling (C8) exists only in the PA channel. The engine also **feeds** REL-6: matchup-born RIVALRY edges are new charged-matchup triggers for future meetings — that is composition, not duplication.

### 2.4 What it writes, what it feeds

- **Writes:** `franchiseRelationshipEdges` rows only (edge create/intensity via the existing `putFranchiseRelationshipEdge` path with sync-engine upsert, `franchiseRelationshipEdgesStorage.ts:111-122`) + morale ledger entries via the L13-5 tap. **No new database** — the 4-registry checklist (backup + sync + L-SIM sandbox + save-slot manifest) is therefore NOT triggered; it applies only if a cached-H2H store ever becomes unavoidable (it should not).
- **Morale → development:** the payoff path is REL-9's locked chain (edge → player morale → development at the 20% checkpoint sweep → True Value). **Dependency:** that chain is currently severed at input — the checkpoint sweep reads the static seeded `player.morale` (`franchiseCheckpointSweepCompute.ts:445`), the ledger has zero write-back (SOT_REGISTER §3.2 "Morale must reach development … DORMANT", :119). Owned by the morale wave; without it the engine's morale effects are ledger-visible but development-inert.
- **Reporter:** narrator-only (C10). Facts adapter emits `{pair, record line, recent-form line, edge born/intensified, charged flag}`; emission rides the dormant relationship flare seam (`franchiseRelationshipFlareEmission.ts:66,104`, zero callers — SOT_REGISTER:237) and the owned 8-dark-emission-kinds wave; LLM seam stays JK-gated.
- **GameTracker:** the existing matchup panel line is untouched and already live (`GameTracker.tsx:5709-5712`); recent-form suffix = OQ-3; no drama widget (C9).
- **Hub/Lens:** matchup edges display wherever edges already display on the Lens (register: "edges display on the Lens", SOT_REGISTER:249) — no new surface.

### 2.5 Cadence summary

Per-game at pCG (event-driven, like overtake): matchup formation check + per-PA morale batch + intensity recompute (which already runs per-game at `processCompletedGame.ts:1437`). The checkpoint-cadence personality formation sweep (`franchiseRelationshipFormationCompute.ts`, checkpoint-boundary-gated) is untouched. Decay: the shipped per-game ramped-decay/dissolve lifecycle (§2.2). No new cadence concept anywhere.

### 2.6 L-SIM note (build-blocking detail)

The lifecycle invariant to extend is `soul.l13-relationship-intensity-lifecycle` (`test-utils/lsim/falsification.ts:284`) — matchup edges must satisfy it at every checkpoint (the 2B precedent). **Trap:** the L-SIM harness has zero `at_bat_events` references (grep of `test-utils/lsim/` — no hits); synthetic games do not populate the event log, so H2H heat is empty/zero under L-SIM. The matchup writer must be a clean no-op on an empty event log, and its invariant must assert the no-op (not require formations). A driven-fixture leg (seed a handful of AB events, assert one formation) is the falsification test.
