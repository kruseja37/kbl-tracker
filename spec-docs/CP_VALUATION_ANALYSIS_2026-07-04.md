# CP Valuation Analysis (2026-07-04)

## BOTTOM LINE

Closers do not look clearly mispriced by the current price curve; keep CP at 0.65 for now. The roster-construction squeeze is real, but it is not mainly because the code models RP stamina or innings better. It happens because the legal roster, pool extractor, BEST-22 designer, roster designer, and auction board all use generic bullpen slots where RP, CP, and sometimes SP/RP compete together. The fix is a roster rule and carve-out: require at least one closer per team and give the pool and board a real closer slot. A price change alone will not force closers into the pool; if JK later wants scarcity included in price, the only narrow change I would consider is CP 0.67-0.68, with a fresh IV oracle re-bless.

## A. CURRENT CP PRICING BASIS

The current arm ladder is implemented directly in the pitcher role curve blocks in `src/data/ivCurves.ts`. The file header says D16 moved pitcher roles onto SP-shaped arm repricing, with only role-scaled blocks differing by role (`src/data/ivCurves.ts:1`, `src/data/ivCurves.ts:7`). Pitcher roles are explicit row keys, including `SP/RP`, `RP`, and `CP` (`src/data/ivCurves.ts:13`, `src/data/ivCurves.ts:18`, `src/data/ivCurves.ts:21`).

The SP block is the 1.00 baseline: VEL midSal/sal100 is 10500/63000, JNK is 5000/20000, and ACC is 7700/34650 (`src/data/ivCurves.ts:162`, `src/data/ivCurves.ts:169`, `src/data/ivCurves.ts:172`, `src/data/ivCurves.ts:173`). The SP/RP block is 0.80 of SP on the same arm shape: VEL 8400/50400, JNK 4000/16000, ACC 6160/27720 (`src/data/ivCurves.ts:176`, `src/data/ivCurves.ts:183`, `src/data/ivCurves.ts:186`, `src/data/ivCurves.ts:187`). The RP block is 0.55 of SP: VEL 5775/34650, JNK 2750/11000, ACC 4235/19060 (`src/data/ivCurves.ts:190`, `src/data/ivCurves.ts:197`, `src/data/ivCurves.ts:200`, `src/data/ivCurves.ts:201`). The CP block is 0.65 of SP: VEL 6825/40950, JNK 3250/13000, ACC 5005/22525 (`src/data/ivCurves.ts:204`, `src/data/ivCurves.ts:211`, `src/data/ivCurves.ts:214`, `src/data/ivCurves.ts:215`).

The IV spec confirms that D16 uses one SP-shaped pitching family with four scalings: SP 1.00, SP/RP 0.80, CP 0.65, RP 0.55 (`spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:14`). The decision register says CP is priced above RP because of leverage, SP/RP is priced below SP because of workload, and flexibility-as-value is deferred rather than double-counted in IV (`spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:94`). The same role multiplier table lists CP at 0.65 and RP at 0.55 with concrete target anchors (`spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:137`, `spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:145`, `spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:146`). The registry later restates `armRoleCurveMultipliers = SP 1.00 / SP-RP 0.80 / CP 0.65 / RP 0.55` (`spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:652`).

The Fable affordability design gives the clearest reason for CP 0.65. It says the role curve block is the sole place the engine expresses role value and that there is no optionality or flexibility knob elsewhere (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:30`). It explicitly keeps RP/CP unchanged and explains CP as roughly 60 innings at leverage index about 1.8, or about 108 leveraged innings, which is about 0.6x SP; RP is roughly 70 innings at leverage index about 1.1-1.3, or about 85 leveraged innings, which is about 0.5x SP (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:38`). The concrete CP targets are the same 0.65 block now in code (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:54`, `spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:61`). The concrete RP targets are the same 0.55 block now in code (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:63`, `spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:70`). The stated acceptance ranges put CP in [0.60, 0.70] and RP in [0.50, 0.60] (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:74`, `spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:79`).

The current CP-over-RP premium is therefore 0.65 versus 0.55, or 0.10 points of SP value. As a ratio, CP is about 18.2 percent above RP. The evidence says that premium represents high-leverage service over ordinary bullpen service. It is not a separate scarcity premium and it is not a separate roster-flexibility premium.

The live salary path uses this role block directly. `buildSalaryIvInput` passes `pitcherRole` into `computeIV` (`src/engines/salaryCalculator.ts:714`, `src/engines/salaryCalculator.ts:738`). The salary IV base is `computeIV(...).kblIV` (`src/engines/salaryCalculator.ts:741`, `src/engines/salaryCalculator.ts:746`). `resolveBlockKey` then selects the pitcher role block for pitcher inputs (`src/engines/ivEngine.ts:193`, `src/engines/ivEngine.ts:202`), and `pitcherKblCells` uses that role to get the pitching block (`src/engines/ivEngine.ts:421`, `src/engines/ivEngine.ts:429`). There is no extra CP salary multiplier: all pitcher entries in `POSITION_MULTIPLIERS` are 1.0, including SP, CP, RP, and SP/RP (`src/engines/salaryCalculator.ts:242`, `src/engines/salaryCalculator.ts:263`).

## B. IS THE PRICE RIGHT?

The current model accounts for closer workload and leverage, but it does not explicitly price the SMB4 last-two-innings mojo-penalty usage cap. The IV spec does document the SMB4 rule: a CP entering before the second-to-last inning gets -1 mojo, and a CP starting gets -2 mojo (`spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:345`, `spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:349`). It also documents role stamina expectations: SP about 70, SP/RP about 45, RP about 25, CP about 20 with fastest recovery (`spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:362`, `spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:365`). The constants exist in code as a CP early-entry penalty and role fatigue thresholds (`src/data/rosterEngineConstants.ts:112`, `src/data/rosterEngineConstants.ts:119`, `src/data/rosterEngineConstants.ts:124`, `src/data/rosterEngineConstants.ts:137`).

Those misuse and fatigue constants are not used by the IV curve itself. The Fable design says CP 0.65 comes from leveraged innings math, not from an explicit last-two-innings penalty term (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:38`). The IV spec says flexibility-as-value is deferred and not double-counted in IV (`spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:94`). Therefore, the correct finding is: the current CP price indirectly reflects limited workload through the 60-inning assumption, but it does not explicitly apply an SMB4 role-misuse discount for the early-entry mojo penalty.

The current model also does not credit CP scarcity as supply scarcity. It credits value-of-service: high-leverage innings. The curve source is the pitcher role block (`src/data/ivCurves.ts:204`, `src/data/ivCurves.ts:215`), the IV spec explains CP > RP as leverage (`spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:94`), and the Fable design quantifies CP > RP as leveraged innings (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:38`). There is no CP scarcity term in the salary path; pitcher roles use the role curve and all pitcher position multipliers remain 1.0 (`src/engines/salaryCalculator.ts:242`, `src/engines/salaryCalculator.ts:263`; `src/engines/ivEngine.ts:193`, `src/engines/ivEngine.ts:202`).

The 0.65 versus 0.55 gap is defensible. The model's own assumptions imply CPs provide fewer innings than RPs but much higher leverage: 108 leveraged innings for CP versus about 85 for RP (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:38`). That ratio is about 1.27x, while the implemented price ratio is only 1.18x. In other words, CP 0.65 already gives closers a haircut relative to pure leveraged-innings math, which is a reasonable way to absorb some of the SMB4 flexibility drag without adding a separate penalty term.

Real-baseball intuition points the same direction. Elite closers commonly create about 1.5-2.5 WAR from roughly 60-70 high-leverage innings, while ordinary middle relievers are often closer to 0.5-1 WAR. That supports CP > RP. SMB4's last-two-innings constraint supports keeping the premium modest rather than pricing CP like a swingman or starter. The current 0.65 does exactly that: CP is above RP, below SP/RP, and far below SP (`spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:14`; `src/data/ivCurves.ts:162`, `src/data/ivCurves.ts:176`, `src/data/ivCurves.ts:190`, `src/data/ivCurves.ts:204`).

Verdict: CP 0.65 is not clearly too low or too high. I would keep it for now. If JK wants CP rarity folded into price rather than handled by roster/pool rules, the narrow future band I would consider is 0.67-0.68, still inside the accepted CP range of [0.60, 0.70] (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:74`, `spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:79`). I would not lower CP below 0.65, because that worsens the roster-construction squeeze without better representing high-leverage value. Any price change would be a future rawIV/kblIV oracle re-bless: the Fable design explicitly requires IV oracle pin updates and re-bless work for arm repricing (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:81`, `spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:86`).

## C. ROSTER-CONSTRUCTION SQUEEZE

The squeeze is real as a roster-construction mechanism. The important correction is that the code does not appear to model RP stamina or innings capacity as a selection advantage in the pool or board systems. The mechanism is bucket competition: CP and RP are both eligible for the same generic bullpen demand, while cheaper-first or budget-repair paths can satisfy that demand with RPs.

### Roster legality

Roster legality does not require a closer. The roster construction file says a legal 22 requires at least four startable arms and at least four relievable arms (`src/data/rosterConstruction.ts:1`, `src/data/rosterConstruction.ts:17`). The legal-count constants include `startingPitchers: 4`, `minRelievers: 4`, and `maxRelievers: 5`, but no closer or CP minimum (`src/data/rosterConstruction.ts:27`, `src/data/rosterConstruction.ts:42`). `canStart` accepts SP or SP/RP, while `canRelieve` accepts RP, CP, or SP/RP (`src/data/rosterConstruction.ts:80`, `src/data/rosterConstruction.ts:87`). `isLegalRoster` enforces four startable pitchers and four relievable pitchers, again without any CP test (`src/data/rosterConstruction.ts:118`, `src/data/rosterConstruction.ts:144`). Therefore, four RPs satisfy bullpen legality without a CP.

### Pool extraction

`draftPoolExtractor` has no CP-specific demand, floor, or carve-out. Its pool structure tracks `startableArms`, `relievableArms`, and `minPitchers`, but no closer or CP count (`src/engines/draftPoolExtractor.ts:45`, `src/engines/draftPoolExtractor.ts:69`). The structural floor logic builds `startableCandidates = source.filter(canStart)` and `relievableCandidates = source.filter(canRelieve)` (`src/engines/draftPoolExtractor.ts:192`, `src/engines/draftPoolExtractor.ts:199`). The reliever floor uses the relievable bucket, where CP, RP, and SP/RP all compete because `canRelieve` accepts all three roles (`src/data/rosterConstruction.ts:84`, `src/data/rosterConstruction.ts:87`). Shortfall messaging is also generic "relief arms" based on `relievable.length` (`src/engines/draftPoolExtractor.ts:200`, `src/engines/draftPoolExtractor.ts:205`).

The extractor then tops up pitcher bodies with all pitchers sorted by IV, again with no CP floor (`src/engines/draftPoolExtractor.ts:207`, `src/engines/draftPoolExtractor.ts:236`). Later pool fill chooses best archetype fit from the remaining source (`src/engines/draftPoolExtractor.ts:314`, `src/engines/draftPoolExtractor.ts:336`), and cap enforcement protects claimed or floor IDs but not CPs as a class (`src/engines/draftPoolExtractor.ts:338`, `src/engines/draftPoolExtractor.ts:355`). Repair rebuilds missing archetype fit and identity players, not closer supply (`src/engines/draftPoolExtractor.ts:358`, `src/engines/draftPoolExtractor.ts:397`). The return object reports floor IDs and verdicts, still without CP-specific output (`src/engines/draftPoolExtractor.ts:411`, `src/engines/draftPoolExtractor.ts:421`).

`poolFromDemand` also collapses CP into generic RP demand unless a demand slot itself is made CP-specific in the future. The file-level comment says the pool is the union of demand-cell reservations plus C1B extractDraftPool floors (`src/engines/poolFromDemand.ts:13`, `src/engines/poolFromDemand.ts:19`). Demand cell keys use `slot.position ?? slot.kind`, so current RP slots become RP-shaped demand rather than CP demand (`src/engines/poolFromDemand.ts:219`, `src/engines/poolFromDemand.ts:224`). Repair-group eligibility for `rp` uses `canRelieve(player)`, so RP, CP, and SP/RP are all valid repair candidates (`src/engines/poolFromDemand.ts:257`, `src/engines/poolFromDemand.ts:271`). The swap-down repair compares salary within class slots (`src/engines/poolFromDemand.ts:301`, `src/engines/poolFromDemand.ts:313`). Repair candidates are filtered by repair class and salary bound, then sorted salary ascending (`src/engines/poolFromDemand.ts:386`, `src/engines/poolFromDemand.ts:394`). Reservations also sort matching-shape candidates by salary ascending (`src/engines/poolFromDemand.ts:535`, `src/engines/poolFromDemand.ts:549`). The final protected ID set includes reserved, claimed, floor, and pinned IDs, but not CPs as a class (`src/engines/poolFromDemand.ts:607`, `src/engines/poolFromDemand.ts:615`).

This confirms JK's concern in one direction and refines it in another. CPs can be squeezed out because nothing requires or protects them. However, the actual code path I found does not prefer RP over CP because it models RP stamina or innings. The preference paths are price, IV, fit, and bucket eligibility.

### Stamina and innings

I found stamina and role-misuse constants, but not stamina or innings-capacity scoring in the pool/board selection paths. `rosterEngineConstants` stores CP early-entry penalty and role fatigue thresholds (`src/data/rosterEngineConstants.ts:112`, `src/data/rosterEngineConstants.ts:137`). The player structures used by construction do not carry a stamina or innings field. `SimPlayer` has IV, salary, position, secondary positions, two-way flag, archetype, and personality fit fields, but no stamina (`src/engines/archetypeBalanceSimulator.ts:30`, `src/engines/archetypeBalanceSimulator.ts:45`). The lower `ConstructionPlayer` interface has ID, name, salary, IV, pitcher flag, role, batting ratings, pitching ratings, and defensive stats, but no stamina or innings (`src/engines/leagueConstruction.ts:63`, `src/engines/leagueConstruction.ts:69`).

The construction objective is IV minus over-budget penalty, not stamina or inning capacity (`src/engines/archetypeBalanceSimulator.ts:166`, `src/engines/archetypeBalanceSimulator.ts:170`). Its shortlist includes top IV, cheapest salary, and best fit (`src/engines/archetypeBalanceSimulator.ts:173`, `src/engines/archetypeBalanceSimulator.ts:189`). Fit grouping puts RP and CP together as `bullpen` (`src/engines/archetypeBalanceSimulator.ts:215`, `src/engines/archetypeBalanceSimulator.ts:220`). Identity-eligible bullpen arms put RP and CP together (`src/engines/archetypeBalanceSimulator.ts:522`, `src/engines/archetypeBalanceSimulator.ts:549`). Identity shortlist sorting uses IV descending, salary ascending, and fit descending (`src/engines/archetypeBalanceSimulator.ts:620`, `src/engines/archetypeBalanceSimulator.ts:635`). The constrained identity climb works through legality, budget, value floor, and fit (`src/engines/archetypeBalanceSimulator.ts:641`, `src/engines/archetypeBalanceSimulator.ts:674`), and the final identity roster evaluates IV, salary, tax, and fit (`src/engines/archetypeBalanceSimulator.ts:755`, `src/engines/archetypeBalanceSimulator.ts:835`).

Draftability and market need are also generic bullpen, not CP-specific. Snipe targets treat RP and CP together for relief corps (`src/engines/draftabilityRanker.ts:84`, `src/engines/draftabilityRanker.ts:97`). Pool depth reasons count relief-capable arms as RP, CP, or SP/RP (`src/engines/draftabilityRanker.ts:120`, `src/engines/draftabilityRanker.ts:126`). Roster need counts pure relief as RP or CP together (`src/engines/rosterNeed.ts:99`, `src/engines/rosterNeed.ts:119`). Hard requirements treat either RP or CP as satisfying bullpen deficit (`src/engines/rosterNeed.ts:255`, `src/engines/rosterNeed.ts:270`). Auction market value is IV times fit times need multiplier times bias (`src/engines/auctionMarketModel.ts:307`, `src/engines/auctionMarketModel.ts:308`), and pure RP/CP players share the same bullpen class (`src/engines/auctionMarketModel.ts:380`, `src/engines/auctionMarketModel.ts:390`). The own-need multiplier depends on hard requirements (`src/engines/auctionMarketModel.ts:398`, `src/engines/auctionMarketModel.ts:407`), and projected target value is IV times fit times need (`src/engines/auctionMarketModel.ts:689`, `src/engines/auctionMarketModel.ts:707`).

Conclusion: JK's squeeze concern is valid, with one correction. The code does not currently appear to select RPs over CPs because it explicitly values RP stamina or innings. It selects generic bullpen bodies using price, IV, fit, need, and legality. Because there is no CP legal requirement, no CP structural floor, and no CP board slot, RPs can satisfy all bullpen demand. Cheapest-first and salary-repair paths make that squeeze especially likely when CPs are more expensive at equal ratings. Value-maximizing paths can still choose a CP if the CP has enough IV or fit, so exclusion is not mathematically guaranteed. But without a requirement and carve-out, CP presence is accidental rather than protected.

## D. RECOMMENDATION FOR JK

### 1. PRICE

Recommendation: keep CP at 0.65 for now.

The evidence supports 0.65 as a conservative high-leverage bullpen price. CP is above RP because of leverage (`spec-docs/IV_ENGINE_AND_ROSTER_INTELLIGENCE_SPEC.md:94`; `spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:38`). CP remains below SP/RP and SP because of lower workload and lower flexibility (`src/data/ivCurves.ts:162`, `src/data/ivCurves.ts:176`, `src/data/ivCurves.ts:190`, `src/data/ivCurves.ts:204`). The implemented CP/RP ratio of about 1.18x is below the Fable leveraged-innings ratio of about 1.27x, leaving a practical discount for the SMB4 usage limitation (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:38`).

Do not lower CP just to reflect the usage cap. The cap is real, but the curve already keeps CP far below starters and swingmen. Lowering CP would also increase the chance that CPs are treated as cheap filler rather than making them structurally present. Do not raise CP merely to solve pool presence either. Raising the price would make required closers harder to afford and still would not guarantee any CP enters the pool.

If JK wants scarcity priced directly into IV, the narrow future change I would put in front of an auditor is CP 0.67-0.68. That is still within the existing CP acceptance band (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:74`, `spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:79`) and would acknowledge rarity without approaching SP/RP. But my recommendation is to keep 0.65 and solve scarcity through roster construction. Any CP price change is a future curve change requiring oracle re-bless discipline (`spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:81`, `spec-docs/FABLE_POOL_AFFORDABILITY_DESIGN_2026-07-04.md:86`).

### 2. ROSTER RULE

Recommendation: require at least one CP per team and carve out a dedicated CP spot in the pool and board.

The requirement is the rule that makes closers non-optional. It would belong first in `rosterConstruction`: the current legal roster only checks startable and relievable counts (`src/data/rosterConstruction.ts:118`, `src/data/rosterConstruction.ts:144`), and `canRelieve` lets RP, CP, and SP/RP satisfy the same bullpen count (`src/data/rosterConstruction.ts:84`, `src/data/rosterConstruction.ts:87`). A future design change should add a closer count, probably a `minClosers: 1` constant and a CP-specific helper, then make `isLegalRoster` enforce it.

The carve-out is the mechanism that prevents the optimizer from substituting a generic RP. It needs to exist in every layer that currently collapses CP into RP. `rosterDesignFeasibility` would need a real CP or closer slot instead of four generic RP slots (`src/engines/rosterDesignFeasibility.ts:69`, `src/engines/rosterDesignFeasibility.ts:78`) and eligibility that does not treat the closer seat as generic `canRelieve` (`src/engines/rosterDesignFeasibility.ts:222`, `src/engines/rosterDesignFeasibility.ts:250`). `draftPoolExtractor` would need CP-specific pool structure and structural floors rather than only `relievableArms` (`src/engines/draftPoolExtractor.ts:45`, `src/engines/draftPoolExtractor.ts:69`; `src/engines/draftPoolExtractor.ts:192`, `src/engines/draftPoolExtractor.ts:205`). `poolFromDemand` would need CP repair and reservation classes that do not collapse to `rp` and `canRelieve` (`src/engines/poolFromDemand.ts:219`, `src/engines/poolFromDemand.ts:224`; `src/engines/poolFromDemand.ts:257`, `src/engines/poolFromDemand.ts:271`).

The board and BEST-22 layers also need the carve-out. `best22Target` currently groups arms only as SP and RP (`src/engines/best22Target.ts:84`, `src/engines/best22Target.ts:113`). `archetypeBalanceSimulator` currently builds four SP slots, four RP slots, and a swing slot (`src/engines/archetypeBalanceSimulator.ts:105`, `src/engines/archetypeBalanceSimulator.ts:133`) while grouping RP and CP together as bullpen (`src/engines/archetypeBalanceSimulator.ts:215`, `src/engines/archetypeBalanceSimulator.ts:220`). `auctionBoardFrame` currently creates four bullpen seats named RP1 through RP4 and fills bullpen with RP or CP (`src/engines/auctionBoardFrame.ts:49`, `src/engines/auctionBoardFrame.ts:75`; `src/engines/auctionBoardFrame.ts:194`, `src/engines/auctionBoardFrame.ts:205`). The roster designer UI should stop using an RP menu for the visible closer slot (`src/src_figma/app/components/leagueBuilder/RosterDesigner.tsx:149`, `src/src_figma/app/components/leagueBuilder/RosterDesigner.tsx:176`, `src/src_figma/app/components/leagueBuilder/RosterDesigner.tsx:180`).

Market and need systems should then distinguish the closer requirement until it is satisfied. `rosterNeed` currently treats RP and CP together for pure relief and hard bullpen requirements (`src/engines/rosterNeed.ts:99`, `src/engines/rosterNeed.ts:119`; `src/engines/rosterNeed.ts:255`, `src/engines/rosterNeed.ts:270`). `auctionMarketModel` inherits that generic hard-requirement model and uses IV, fit, need, and bias to value players (`src/engines/auctionMarketModel.ts:307`, `src/engines/auctionMarketModel.ts:308`; `src/engines/auctionMarketModel.ts:398`, `src/engines/auctionMarketModel.ts:407`).

Interaction summary: cheaper CPs help affordability if a closer becomes required, but price does not force closers into the pool. The require-and-carve-out rule is what actually guarantees CP inclusion. Price answers whether CPs are fair once included. The roster rule answers whether CPs appear at all.
